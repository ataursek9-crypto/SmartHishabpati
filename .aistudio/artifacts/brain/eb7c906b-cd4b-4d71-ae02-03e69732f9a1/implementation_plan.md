# SmartHishabpati – Google Account Registration ও Super Admin Real Shop List স্থায়ী সমাধানের Implementation Plan

## সারসংক্ষেপ (Executive Summary)
এই পরিকল্পনার মূল উদ্দেশ্য হলো **SmartHishabpati** অ্যাপে Google Authentication-এর মাধ্যমে নতুন দোকান রেজিস্ট্রেশন, একই Gmail অ্যাকাউন্টের অধীনে একাধিক দোকান তৈরি ও পরিচালনা, Super Admin ড্যাশবোর্ডে শুধুমাত্র Firestore-এর বাস্তব দোকান প্রদর্শন (ডেমো সিড ডেটা সম্পূর্ণ অপসারণ), এবং Revoked অ্যাকাউন্টের ক্ষেত্রে সাধারণ দোকানদার হিসেবে পূর্ণ স্বাধীনতা নিশ্চিত করা। 

বর্তমানে `buddavaibinodon@gmail.com` Firebase Auth-এ Google Sign-In Provider দিয়ে সফলভাবে নিবন্ধিত থাকলেও Firestore `/businesses`-এ কোনো দোকান না থাকায় লগইন ও রেজিস্ট্রেশন প্রক্রিয়ায় ডেডলকে (Deadlock) আটকে যায়। এই প্ল্যানের মাধ্যমে আর্কিটেকচারাল সমাধান প্রদান করা হয়েছে যাতে বিদ্যমান ডেটা অক্ষত রেখে সিস্টেমটি শতভাগ স্কেলেবল ও নিরাপদ হয়।

> **নিশ্চিত নীতিসমূহ (Guaranteed Decisions):**
> 1. **জিরো ডেটা লস (Zero Data Loss):** বিদ্যমান কোনো বাস্তব দোকানের তথ্য, পণ্য বা হিসাব ডিলিট করা হবে না।
> 2. **কোড পরিবর্তন স্থগিত:** এই ধাপে কোনো সোর্স কোড বা ডেটাবেস পরিবর্তন করা হবে না; শুধুমাত্র অনুমোদিত প্ল্যান উপস্থাপন করা হচ্ছে।
> 3. **সুপার অ্যাডমিন অনুমতি:** শুধুমাত্র `ataurgonee4@gmail.com`, `ataursek9@gmail.com` এবং `01700000000` সুপার অ্যাডমিন হিসেবে বহাল থাকবে। `buddavaibinodon@gmail.com` সুপার অ্যাডমিন হিসেবে বাতিল (Revoked) থাকবে, কিন্তু সাধারণ দোকানদার হিসেবে স্বাধীনভাবে একাধিক দোকান তৈরি ও পরিচালনা করতে পারবে।

## ১. Google দিয়ে নতুন দোকান তৈরি (Fixing EMAIL_EXISTS & Deadlock)

### ১.১ বর্তমান সমস্যার মূল কারণ (Root Cause Analysis)
* ব্যবহারকারী যখন `buddavaibinodon@gmail.com` দিয়ে আগে একবার "Google দিয়ে লগইন করুন"-এ ট্যাপ করেছিলেন, তখন Firebase Authentication-এ স্বয়ংক্রিয়ভাবে একটি Firebase User রেকর্ড (UID সহ) তৈরি হয়েছিল।
* কিন্তু Firestore-এর `/businesses` কালেকশনে তার কোনো সক্রিয় দোকান না থাকায় `BusinessViewModel.handleGoogleUserCredentials()` তাকে রিজেক্ট করে নতুন দোকান খোলার পরামর্শ দেয়।
* এরপর ব্যবহারকারী যখন `ShopRegistrationScreen`-এ গিয়ে নিজের ইমেইল `buddavaibinodon@gmail.com` এবং ৬-সংখ্যার পিন দিয়ে "যাচাই কোড পাঠান" চাপেন, তখন কোডের ধাপ ৩-এ সরাসরি কল করা হয়:
  ```kotlin
  viewModel.registerWithEmailPassword(cleanEmail, registrationPassword)
  ```
* Firebase Auth এর বিল্ট-ইন নিয়মানুযায়ী `createUserWithEmailAndPassword()` কল করলে ত্রুটি আসে:
  `FirebaseAuthUserCollisionException: The email address is already in use by another account.`
* ফলে রেজিস্ট্রেশন স্ক্রিন ব্যবহারকারীকে `"এই জিমেইল দিয়ে ইতিমধ্যে একটি অ্যাকাউন্ট রয়েছে। দয়া করে লগইন করুন।"` দেখিয়ে আটকে দেয়। কিন্তু লগইন করতে গেলে পাসওয়ার্ড নেই (যেহেতু অ্যাকাউন্টটি Google Provider দিয়ে তৈরি) এবং দোকানও নেই। এতে ব্যবহারকারী সম্পূর্ণ আটকে পড়েন।

### ১.২ প্রস্তাবিত সমাধান (Architecture & UX Flow)
1. **Google একাউন্ট অটো-ডিটেকশন ও ওয়ান-ট্যাপ ভেরিফিকেশন:**
   * রেজিস্ট্রেশন উইজার্ডের ৩য় ধাপে একটি বিকল্প যুক্ত করা হবে: **"Google দিয়ে সরাসরি যাচাই ও যুক্ত করুন"**।
   * ব্যবহারকারী যদি ম্যানুয়ালি ইমেইল টাইপ করে এবং Firebase Auth থেকে `EMAIL_EXISTS` / `already in use` এরর আসে, তখন অ্যাপ এরর দিয়ে আটকে না রেখে একটি সুন্দর পপআপ বা প্রম্পট দেবে:
     > *"এই জিমেইলটি ইতিমধ্যে গুগল সাইন-ইন দিয়ে নিবন্ধিত। আপনার গুগল অ্যাকাউন্ট দিয়ে নিশ্চিত করে দোকান রেজিস্ট্রেশন সম্পন্ন করুন।"*
   * নিচে একটি বাটন থাকবে: **[ Google দিয়ে নিশ্চিত করুন ]**।
2. **অথেনটিকেশন ও দোকান ক্রিয়েশন প্রবাহ:**
   * Google Sign-In সফল হলে প্রাপ্ত `FirebaseUser.uid` এবং `FirebaseUser.email` ব্যবহার করে সরাসরি ধাপ ৪ বাইপাস করে (যেহেতু গুগলের ইমেইল ইতিমধ্যে গুগল কর্তৃক ভেরিফাইড) Firestore-এ নতুন দোকান তৈরি করা হবে:
     ```kotlin
     viewModel.registerNewShop(
         shopName = shopName,
         ownerName = fullOwnerName,
         phone = phone,
         address = address,
         district = district,
         businessType = selectedBusinessType,
         pin = pin,
         isPhoneVerified = false,
         ownerEmail = googleUser.email,
         ownerUid = googleUser.uid
     )
     ```
   * এভাবে কোনো পাসওয়ার্ডের সংঘর্ষ হবে না এবং ব্যবহারকারী নিজের গুগল আইডির অধীনে দোকান পেয়ে যাবেন।

## ২. একই Gmail দিয়ে একাধিক দোকান পরিচালনা (Multi-Shop Support)

### ২.১ মাল্টি-টেন্যান্ট ডেটা মডেল (Multi-Tenant Data Model)
* **দোকান আইডি স্ট্রাকচার:** পূর্বে কিছু ক্ষেত্রে ব্যবহারকারীর `uid` সরাসরি `businessId` হিসেবে ব্যবহৃত হয়েছিল, যা একই ইউজারের অধীনে একাধিক দোকান খোলার পথে বাধা ছিল।
* **নতুন কাঠামো:** প্রতিটি দোকানের জন্য একটি অনন্য বিজনেস কোড/আইডি তৈরি হবে:
  `biz_{timestamp}_{random4}` (উদাহরণ: `biz_1730761234_8921`)।
* প্রতিটি দোকানের ডকুমেন্টে থাকবে:
  * `id`: unique business id
  * `ownerUid`: ব্যবহারকারীর Firebase UID
  * `ownerEmail`: ব্যবহারকারীর জিমেইল (ছোট হাতের অক্ষরে)
  * `businessName`: দোকানের নাম
  * `ownerPhone`: মোবাইল নম্বর
  * `createdAt`: রেজিস্ট্রেশন টাইমস্ট্যাম্প
* এছাড়া ইউজারের অধীনে সব দোকানের ইনডেক্স রাখতে `/users/{uid}/shops/{businessId}` অথবা কেন্দ্রীয় `/businesses` থেকে `whereEqualTo("ownerUid", uid)` কোয়েরি চালানো হবে।

```
                                │   UID: "PBknnhTZ1LNZsNBb9dp..."      │

                                                   │
                        ┌──────────────────────────┴──────────────────────────┐
                        ▼                                                     ▼
        ┌───────────────────────────────┐                     ┌───────────────────────────────┐
        │       দোকান ১ (Shop 1)         │                     │       দোকান ২ (Shop 2)         │
        │ ID: "biz_1730761234_8921"     │                     │ ID: "biz_1730765678_4312"     │
        │ Name: "বিনোদ স্টোর (মিরপুর)"   │                     │ Name: "বিনোদ ফ্যাশন (উত্তরা)"  │
        │ ownerUid: "PBknnhTZ..."       │                     │ ownerUid: "PBknnhTZ..."       │
        └───────────────┬───────────────┘                     └───────────────┬───────────────┘
                        │                                                     │
        ┌───────────────┴───────────────┐                     ┌───────────────┴───────────────┐
        │  /products, /sales, /customers│                     │  /products, /sales, /customers│
        │  (সম্পূর্ণ বিচ্ছিন্ন ডেটাবেস)     │                     │  (সম্পূর্ণ বিচ্ছিন্ন ডেটাবেস)     │
        └───────────────────────────────┘                     └───────────────────────────────┘
```

### ২.২ লগইন প্রবাহ ও দোকান নির্বাচন স্ক্রিন (Shop Selector Flow)
1. ব্যবহারকারী যখন Google Sign-In সম্পন্ন করবেন, `BusinessViewModel` ক্লাউড Firestore থেকে ইউজারের সব দোকান খুঁজে আনবে:
   `firestore.collection("businesses").whereEqualTo("ownerUid", uid).get()`
2. **ফলাফল হ্যান্ডলিং:**
   * **০টি দোকান পাওয়া গেলে:** সরাসরি রেজিস্ট্রেশন স্ক্রিনে নিয়ে যাবে ("আপনার কোনো দোকান নেই, দোকান তৈরি করুন")।
   * **১টি দোকান পাওয়া গেলে:** কোনো ডায়ালগ ছাড়াই সরাসরি সেই দোকানে প্রবেশ করাবে (`activeBusinessId` সেট হবে)।
   * **২ বা ততোধিক দোকান পাওয়া গেলে:** একটি পরিষ্কার ও সুন্দর **"দোকান নির্বাচন করুন" (Select Your Shop)** ডায়ালগ/বটমশীট দেখানো হবে:
     * প্রতিটি দোকানের নাম, ঠিকানা/শাখা এবং রোল (অ্যাডমিন) কার্ড আকারে প্রদর্শিত হবে।
     * ব্যবহারকারী যে দোকানে ট্যাপ করবেন, সেই দোকানের `businessId` অ্যাপের `activeBusinessId` হিসেবে সেট হবে।
3. **ডেটা আইসোলেশন (Data Isolation Guarantee):**
   * লোকাল Room ডেটাবেসে প্রতিটি টেবিলে (`products`, `customers`, `sales`, `expenses`, `users`) `shopId` ফিল্টার কঠোরভাবে প্রয়োগ করা হবে।
   * Firestore সাব-কালেকশন সবসময় `/businesses/{selectedShopId}/*` পাথে থাকবে। ফলে দোকান ১-এর পণ্য, বাকি বা খরচের হিসাব কখনোই দোকান ২-এর সাথে মিশ্রিত হবে না।
   * অ্যাপের শীর্ষ বার (TopBar) বা মেন্যু থেকে যেকোনো সময় **"দোকান পরিবর্তন করুন" (Switch Shop)** অপশনের মাধ্যমে অন্য দোকানে সুইচ করা যাবে।

## ৫. Firebase ও Security Rules পরিবর্তনের পরিকল্পনা

### ৫.১ বর্তমান রুলসের বিশ্লেষণ
* বর্তমানে `firestore.rules`-এ `businesses/{businessId}` তৈরি করার শর্ত:
  ```javascript
  allow create: if isSuperAdmin() || (
    isSignedIn() && (
      request.auth.uid == businessId ||
      incoming().ownerUid == request.auth.uid ||
      (!('ownerUid' in incoming()) && request.auth.uid == businessId)
    ) &&
    isValidNewShopRegistration(incoming(), businessId) &&
    ...
  );
  ```
  এটি ইতিমধ্যে নতুন তৈরি হওয়া দোকানের ক্ষেত্রে `incoming().ownerUid == request.auth.uid` সাপোর্ট করে।
* কিন্তু একই ইউজারের একাধিক দোকান রিড করার জন্য `allow list` রুলটি আরও সুনির্দিষ্ট ও নিরাপদ করতে হবে:
  ```javascript
  allow list: if isSuperAdmin() || (
    isSignedIn() && (
      resource.data.ownerUid == request.auth.uid ||
      (request.auth.token.email != null && 'ownerEmail' in resource.data && resource.data.ownerEmail == request.auth.token.email.lower())
    )
  );
  ```

### ৫.২ নতুন প্রস্তাবিত কালেকশন ও রুলস সংযোজন
1. **মাল্টিপল শপ ওনারশিপ ভ্যালিডেশন:**
   * কোনো দোকানদার যাতে অন্য কারো দোকানের ডেটা পড়তে বা পরিবর্তন করতে না পারে, তার জন্য প্রতিটি সাব-কালেকশনে (`products`, `customers`, `sales`, `expenses`, `staff`) বর্তমান `isBusinessStaff(businessId)` অপরিবর্তিত থাকবে:
     ```javascript
     function isBusinessOwner(businessId) {
       return isSignedIn() && (
         isSuperAdmin() ||
         (exists(/databases/$(database)/documents/businesses/$(businessId)) &&
          get(/databases/$(database)/documents/businesses/$(businessId)).data.ownerUid == request.auth.uid)
       );
     }
     ```
   * ফলে দোকানদার ১ তার নিজের ইউআইডি-যুক্ত দোকান ছাড়া অন্য কোনো দোকানের ডকুমেন্টে একবিন্দু অ্যাক্সেস পাবে না।
2. **সুপার অ্যাডমিনের জন্য কেন্দ্রীয় অ্যাক্সেস:**
   * সুপার অ্যাডমিন (`isSuperAdmin()`) পূর্বের মতোই সকল দোকানের তালিকা ও বিবরণ কেন্দ্রীয়ভাবে মনিটর করতে পারবেন, কিন্তু কোনো সাধারণ দোকানদার এই অনুমতি পাবে না।
